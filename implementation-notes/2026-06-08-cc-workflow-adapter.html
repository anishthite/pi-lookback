cc-workflow source adapter

Task: implement cc-workflow source adapter for pi-lookback per spec from planner subagent. Append-only log.

Decisions

idwhatwhy
D-1Adapter exports both sniff(filePath,firstLine) and a new optional sniffFile(filePath). sniffSource extended with a second pass that tries sniffFile on adapters that export it.Pretty-printed JSON ⇒ readFirstJsonLine returns null ⇒ adapters never get called. The two-pass design keeps pi/cc on the cheap O(1) firstLine path and only opens the file when nothing else claimed it.
D-2Synthesize 1 leading kind:'user' + N kind:'assistant' entries.Avoids special-casing summary.js (firstPrompt/userMessageCount/firstUser lookups all work). Cost = one fake row.
D-3sessionMeta.cwd = doc.scriptPath.Library row's project column shows the workflow script path — most useful affordance per spec §5.
D-4Linear timestamp interpolation across [startedAt, finishedAt].Journal items have no timestamps; library/trace UI assume monotonic order.
D-5decodeProjectDir() returns empty string.projectKey is a runId, not an encoded path; nothing useful to decode. summary's resolveProjectPath chain hits cwd first anyway (D-3).
D-6Early-return null for cc-workflow in buildInitialInput.Workflows have no "initial input" concept; falling through to pi path would call loadProjectContextFiles against a file (scriptPath), not a dir, risking explode.
D-7Registry order: pi, claude-code, cc-workflow.cc-workflow's sniffFile opens a file; pi/cc decide on the already-read first line. Putting cc-workflow last preserves cheap paths.
D-8Update setSessionsRoot(root) back-compat shim to also pass 'cc-workflow': null.So existing tests that mount FIX as pi-only don't leak cc-workflow rows from $HOME.

Tradeoffs

T-1Synthetic user vs. patching summary.js: chose synthetic (D-2) over conditional firstPrompt logic. Net: tiny over-count on userMessageCount but zero churn in summary.js (used by both pi+cc).
T-2Two-pass sniff vs. a registered "I always claim .json files" adapter: two-pass keeps the contract minimal and per-adapter cost is bounded (64KB read, only when first pass fails).

Open / followups

L-1public/app.js initial-input ternary will pick the pi message for cc-workflow source. Backend returns null so the UI shows the empty state — acceptable, but the message text is misleading if someone reads it. Frontend out-of-scope per task constraints; flag for reviewer.
L-2If journals ever exceed a few MB, JSON.parse entire file is suboptimal. Same 256MB hard cap as siblings; document as known limitation.
