Cache-bust investigation

Task: Figure out why we are having prompt-cache busts in pi sessions; explain the busts in the longest 10 sessions; recommend fixes. Lab notebook, append-only.

H — Hypotheses for why Anthropic prompt cache busts in pi

Anthropic's prompt cache keys on the exact byte prefix of {system + tools + messages} for a given model. The cache also has a TTL (5 min default, 1 h with the cache_control: {type: ephemeral, ttl: "1h"} beta). A "bust" = the next turn reads back fewer cached tokens than it should, forcing a fresh write of the prefix.

The candidate root causes I will test against the data:

H2Model change mid-sessionmodel_change event preceding the bust; cacheRead → 0 on next assistant

D-1 — JSONL schema notes (observed)

  usage          : {input,output,cacheRead,cacheWrite,totalTokens,cost{...}}
toolResult, bashExecution, compaction, branch_summary, custom, custom_message

Key telemetry: message.usage.cacheRead and message.usage.cacheWrite on assistant messages. A cache bust = turn n+1 reads back materially less than turn n cached.

D-2 — Detector definition

For each session, walk assistant messages with a usage block in order. Let prefix_n = cacheRead_n + cacheWrite_n (total cached prefix that existed at end of turn n). Expected: cacheRead_{n+1} ≥ prefix_n − epsilon minus whatever the user input added. A bust is flagged when:

bust if  cacheRead_{n+1}  <  0.5 * prefix_n   AND   prefix_n > 5000
size of bust = prefix_n − cacheRead_{n+1}    (tokens lost)

Then attribute the bust by inspecting events between turn n and turn n+1 (the "interlude") in this priority order: compaction → model_change → thinking_level_change → branch event → time gap > 5min (H1) → tool-set change (H6) → none-detected (H7/H8/H9 candidate).

D-6 — KEY FINDING #4: live, reproducible bust mechanism observed in THIS session

While generating this notebook the context-mode extension was injecting a <pruner-note>N unpruned tool call result(s) currently in context…</pruner-note> tag onto user/tool-result messages. The integer N incremented on every turn (26 → 27 → 28 within minutes). That text is not in the JSONL — pi's JSONL records the canonical conversation, not the wire-augmented payload — but it IS sent to the model. Any cache_control breakpoint placed at or after that injection rotates per turn → guaranteed bust unless the breakpoint is positioned strictly before it on every turn.

That explains why our regex for <pruner-note> across all 377 JSONL files returns 0 hits, yet sessions with extensions still bust 3× more often.

D-7 — Recommended fixes (ranked)

  1. F1 — Pin two long-lived cache_control breakpoints, not four sliding ones.
    Place breakpoint #1 at end-of-system+tools (covers ~12k–40k of static tokens). Place breakpoint #2 on the oldest stable user/assistant turn and only advance it when it has clearly fallen out of relevance — never on every turn. Reserve breakpoint #3 for the last-but-one turn and #4 for the current turn. Most pi sessions seem to advance the breakpoints one-per-turn, which guarantees the 4-cap exhaustion plateau we see. Expected impact: eliminate the ~55% breakpoint-exhaustion class.
  2. F2 — Treat all on-the-wire reminders as "outside the cache zone".
    Every dynamic system reminder (pruner-note, env block, active-skills list, todo state, intercom message, cwd indicator, current date line) must be appended after the last cache_control marker on the request, so the cached prefix is invariant. Also, where possible, round/bucket the values so consecutive turns produce identical text (e.g., "≥10 unpruned" instead of the exact count). Expected impact: ~25% reduction.
  3. F3 — Enable Anthropic's 1-hour extended-cache-ttl-2025-04-11 beta for the static system+tools breakpoint.
    The 5-min default TTL is the proximate cause of 475 busts in the corpus and dominates multi-day sessions. Bump TTL on the bottom-of-prefix block where the marginal write cost (~2×) pays back instantly on the first re-read after 5 min idle. Expected impact: ~12% reduction.
  4. F4 — Track and surface in pi-lookback. Add a per-session "cache health" signal: detect cacheRead plateaus and large prefix→read drops with no visible cause, and tag the session for review. Add UI columns: cacheBusts, lostCacheTokens, plateauValue.
  5. F5 — Audit hook/extension authors: the pi-context-prune extension is the single biggest contributor (source: pi-context-prune/src/reminder.ts :: annotateWithUnprunedCount; it appends the reminder to the last ToolResultMessage's content on every turn). Patch pi-context-prune to either:
    • quantize the unpruned count ("some" / "many"), OR
    • emit the reminder once-per-session at session start instead of every turn, OR
    • place the reminder in a position that is provably after every cache_control marker pi will emit.
  6. F6 — Discourage mid-session model swaps (and especially provider swaps): document the full-prefix re-write cost; show a warning in the TUI before switching.
  7. F7 — Append-only pruning: never rewrite prior assistant/tool messages in place. Pruner output should be a fresh user message ("previously: …") and the old messages either kept verbatim or replaced with a stable-byte placeholder (same length, same hash) for cache stability.

Strategy in plain English: 1 breakpoint on system prompt (2 when OAuth/Claude Code identity is also marked), 1 breakpoint on the last user/tool-result message. Total ≤3. Anthropic's per-request cap is 4, so this never trips the cap. H10 as originally stated (breakpoint-exhaustion) is FALSIFIED.

T-2 — Revised mechanism for the plateau: Anthropic's cache returns the longest prefix whose bytes match a previously-cached request. With 2 markers (system, last-user) the cache will hit on system+tools if those are byte-identical, and additionally hit on conversation messages up to the first byte-divergence. The plateau pinning cacheRead at exactly the static prefix means some byte inside the conversation history changes every turn, killing the read at the first such message. Marker count is irrelevant — the byte-prefix is what matters.

D-16 — Restated H10 (root cause): WIRE-TIME RE-SERIALIZATION of historical messages with rotating content. Every turn, pi re-builds the full params.messages array by walking the in-memory session state. If any per-turn-mutating field (e.g. pruner-note counter, system-reminder injected onto an old tool-result, env block re-stamped on an old user msg, todo-state re-injected) is re-applied to historical messages at every build, the cached prefix only matches up to that injection point. Evidence: the live <pruner-note>N…</pruner-note> integer increments per turn (L-11 captured N=26..57) and 0/377 JSONL files contain that string — proving the mutation lives in the wire builder, not the canonical session log.
