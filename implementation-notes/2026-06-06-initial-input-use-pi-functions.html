Initial-input reconstruction — switch to pi's own exported functions

Task. User said: "ok, can you make sure that pi lookback reconstructs the initial system prompt exactly as pi does it using the function from pi". Follow-up to 2026-06-06-initial-request-modal: the v1 hand-rolled assembly drifted from pi (over-listed ~/.codex/AGENTS.md/~/.gemini/GEMINI.md as separate entries because pi only reads ~/.pi/agent/AGENTS.md from home; symlink dedupe was string-based not realpath-based; skill loader had its own walking rules; tool/guideline composition was duplicated).

Decisions

iddecisionwhy
D-1Dynamic-import pi's ESM bundle from the resolved install dir and delegate to its exports: buildSystemPrompt, loadProjectContextFiles, loadSkills, formatSkillsForPrompt, getAgentDir.pi-lookback is CJS, pi is ESM ("type":"module"). Dynamic import() is the only bridge. pi already exports exactly these from dist/index.js.
D-2The canonical system-prompt string is whatever pi.buildSystemPrompt(opts) returns — not our own concatenation. Labeled sections still exist for the UI but their text values are derived from the SAME inputs we pass to pi, and a runtime assertion checks sections.map(s=>s.text).join('') === piRendered."Exactly as pi does it" requires the byte-for-byte string to come from pi. The labeled view stays for UX (highlight which file produced which substring), but its correctness is now verified against the pi truth.
D-3buildInitialInput() becomes async; api.getInitialInput() becomes async; server.js route handler awaits it.Dynamic import is async. No way around it for CJS callers of an ESM module.
D-4If the dynamic import fails (pi not installed in a discoverable path), fall back to the legacy hand-rolled assembly with a notes warning.pi-lookback ships without pi as a dep. We shouldn't 500 when pi is absent — the legacy path is still correct enough for the modal to render, just with the historical caveats.
D-5Drop ~/.claude, ~/.codex, ~/.gemini from the home-dir candidate list. pi never reads those.Removing the bug. pi's loadProjectContextFiles only reads from agentDir (~/.pi/agent) and the cwd walk. The symlinks at those other home dirs are for other agent tools, not pi.
D-6Skills load via loadSkills({ cwd, agentDir, skillPaths: [], includeDefaults: true }), then formatSkillsForPrompt(skills) for the rendered text. disableModelInvocation filtering is done inside formatSkillsForPrompt already.pi's loader does symlink-realpath dedupe + collision detection + extension-skill discovery. We were reimplementing a worse version of all of this.

Tradeoffs

idtradeoff
T-1Async API breaks any in-process caller that expected sync. Audited: only server.js handleApi calls api.getInitialInput; that handler is wrapped in try/catch and can become async safely.
T-2Dynamic import of a non-dep package is brittle — if the user's pi install moves, we lose byte-exactness and fall back. Mitigated by reusing the existing candidatePiInstallDirs() resolver and surfacing the fallback in the response notes.
T-3We can't see CLI overrides (--system-prompt, --append-system-prompt, --no-skills, custom tool sets) from the JSONL, so the reconstruction is still "what pi would send with defaults today". Unchanged from v1, still surfaced in notes.

Open questions

idquestion
Q-1pi's getAgentDir() uses $HOME/.pi/agent. If a user sets PI_HOME or similar at session run time and we don't see that in the JSONL, our reconstruction will read the default location. Probably fine for v1.
